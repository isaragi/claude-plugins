# 背景を伝えない PR レビュー

作った本人の説明に引きずられないよう、レビューは何も知らない別のエージェントに任せる。

## 依頼文に書くもの（これだけ）
- リポジトリの場所と PR 番号
- 下の「レビューの観点」
- 作業の制約（変更・マージをしない、使ってはいけない資源（シミュレーターなど）、検証用 worktree の場所と後片付け）
- 出力の形：最初の行に「判定：マージしてよい」または「判定：直してからマージ」、根拠を短く、直すべき点は箇所と修正案

## 依頼文に書かないもの
- 自分の設計の理由、気をつけてほしい点、「こう直した」という説明
- 前回のレビューの指摘とその直し方（再レビューでも書かない。いまの状態だけを見てもらう）
- ユーザーとのやり取り

材料は、レビュー担当が自分で集める：`gh pr view`、`gh pr diff`、`gh pr checks`、PR 本文から辿れる issue、CLAUDE.md、コード。PR 本文は、人のレビューでも読む材料なので含めてよい。

## レビューの観点（依頼文にそのまま入れる）
1. PR の目的と、issue で決まったことに実装が合っているか
2. ロジックの正しさ（境界、反例、想定される使い方での振る舞い）。数値で確かめられるものは確かめる
3. 設計（既存コードとの一貫性、状態遷移、並行処理）
4. テストの網羅と質
5. ドキュメント・コメント・PR 本文と実装の一致
6. 画面の変更があれば、スクリーンショット（ライト・ダーク、変更前後）が揃っていて、見た目に問題がないか
7. CI のチェック

## レビューのあと
- 「直してからマージ」なら直して push し、また何も知らないエージェントに新しくレビューしてもらう。
- 任意の指摘も、手間が小さければ入れる。
- 「マージしてよい」かつ CI がすべて通ったら、判定の要旨を PR にコメントしてからマージする（下書きなら Ready にしてから）。
- ユーザーの判断が要る PR（デザインの選択、文言の方針、費用、取り消しにくいこと）は、レビューが通ってもユーザーに確認する。
