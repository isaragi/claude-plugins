# ペルソナのパネルで決める

ユーザーに選ばせる前に、想定する利用者と専門家のパネル（シミュレーション）に意見を聞いて決める。

## パネルにかけるもの・かけないもの
- かけないもの：デザイン（モック・ワイヤーフレーム）に描かれている所と、決まったこと（前の段の決定・ユーザーが目標として言ったこと）から導ける所。細かい部分は、デザインを手本にして作る。パネルにかけて決め直さない。
- かけないもの：測れるもの（音質・性能・容量・ライセンスなど）。測って決める。
- かけるもの：どこからも決まらない、本当に新しいものだけ。かける前に「これはデザインや決定から導けないか」を 1 つずつ確かめる。

## 進め方
1. **パネルを組む**：12人以上。実際の利用者の幅を入れる。
   - 例（子ども向けアプリ）：対象年齢の子ども数人（得意な子・苦手な子・左利き・字が読めない子）、共働きの親、ひとり親、祖父母、その分野の専門家（講師など）、保育士、アクセシビリティに配慮が要る人（弱視・聴覚・ADHD の子の親）、アプリのデザイナー、ストア審査に詳しい人、海外の利用者
2. **渡すものを決める**：端末・場面の事実、アプリの目的（何をいちばん大事にするか）、決まったこと（デザイン・前の段の決定）を前提として渡す。下の「問いの書き方」と「ユーザーの言葉の扱い」に従う。
3. **開かれた質問にする**：「A と B のどちらがよいか」と二択にしない。「この画面を見てどう感じるか」「困りそうなところは」「どうしたいか」と聞く。
4. **見せられるものは見せる**：画面ならスクリーンショットやモックの画像を Read で見られる場所に置いて、具体的な箇所を指して答えてもらう。見せられないものは下の「確かめられないもの」に従う。
5. **出力の形**：各人の短い意見、論点ごとの集計（票）と結論、少数意見のうち取り入れるべき点、実装の前に直すべき点、パネルが確かめられなかったこと。
6. **記録する**：結論を関係する issue にコメントで残す（日付・人数・票）。

## 問いの書き方
- 問いに答えの形（分ける・切り替える・A か B か）を入れない。既存の作り方や決まった解決策を前提として入れ、その中の細部だけを聞くことをしない（例：「半開きのときに上下に分ける」と決めた上で「いつ分けるか」だけを聞く、はだめ）。「何も特別なことをしない」も答えの 1 つ。
- 白紙にするのは、まだ決まっていない所だけ。決まったデザインは手本・前提として渡す（パネルにも、作りを任せるエージェントにも）。
- ほかのアプリ（同じ作者の別のアプリを含む）の作りは、答えの候補として渡さず、結果と並べて比べる材料にする。
- 問いを書いたら、出す前に、答えの形・自分の見立て・期待する答えが入っていないかを読み直す。サブエージェントで回す場合も、依頼文に自分の見立てを書かない。

## ユーザーの言葉の扱い
- ユーザーの言葉が、その決定の目標（例：「可愛らしい音に」「聞いていたくなる音に」）のときは、伏せずに目標として渡す。目標を伏せると、パネルが目標と逆の結論を出すことがある。
- 伏せるのは、決定ではない意見だけ（試作を触った感想、思いつきの好み）。伏せて聞いたら、結論のあとで並べて報告する（パネルを誘導しない）。
- どちらか迷ったら、ユーザーがそれを「こうしたい」と決めたのか、「こう感じた」と言ったのかで分ける。

## 確かめられないもの
- パネルは音・動き・手触りを直接は確かめられない。画像は見られても、実機で見たときの大きさ・明るさ・速さは分からない。
- 音や動きは、測った数字（周波数・音量・長さ・立ち上がり・テンポ・寸法・コントラスト比など）と、何がどう鳴る・動くかの記述で渡す。
- 結果には、パネルが何を数字と記述でしか見ていないかを書き、実際に確かめる手段（試聴ページ、録画、実機での確認）を添える。

## 気をつけること
- 結果には必ず「シミュレーションであり、実在の人の意見ではない」と書く。
- パネルの票は、取り消しにくい操作（公開・購入・削除・main への push）の許可にはならない。
