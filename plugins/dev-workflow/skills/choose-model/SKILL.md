# サブエージェントのモデルと指示を決める

## 出典と、印の読み方
各項目の末尾の印が出典を示す。【運用】は、出典にない、このプラグインの運用の決まり。数字は、出典が自社の計測として挙げたもの。リポジトリや作者の決まり（CLAUDE.md）と食い違ったら、そちらに従う。

- 【B】claude.dev のブログ「Which Claude model should you build with?」（2026-11-09）：https://claude.dev/blog/which-claude-model-should-you-build-with/
- 【F】ドキュメント「Prompting Claude Fable 5.2」：https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-fable-5-2
- 【O】ドキュメント「Prompting Claude Opus 5.5」：https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-opus-5-5

API を自分で呼ぶときの話（thinking の表示の設定、ベータのヘッダー、`tool_choice`、履歴の編集と 400 エラー、`max_tokens`、移行の互換性）は、このスキルでは扱わない。必要なら出典を直接読む。

## 決める順
1. **任せるかどうか**
   - 任せないもの：1 つの文脈に収まる作業。手順が 1 本につながった作業。分ける・まとめる手間が、節約を上回るため【B】。
   - 任せるもの：互いに依存しない作業、メインの文脈を汚す大量の読み込み（ファイルの総ざらい・ログ・長い出力）【B】。別の目で見てほしいもの【運用】。
   - メインの文脈は軽く保ち、判断に使う。冗長な読みは安いサブエージェントに渡す【B】。
   - サブエージェントは、セッションの費用の大部分になりうる【F】。
2. **確かめる手段を先に用意する**
   - テスト・ビルド・エンドポイントを呼ぶスクリプトで、モデルが自分の作業を確かめられるようにする。
   - 確かめる手段を足すほうが、effort を上げるより安く、速いことが多い【B】。
3. **effort を 1 段上げる**（Agent ツールの `effort: "higher"`）
   - effort を上げると、長く考える・ツールを多く呼ぶ・自分の成果を確かめるようになる。遅くはなる。知識や技能は増えない【B】。
   - high を超える 1 段は、上のモデルに替えるのと同じくらいかかる【B】。
4. **それでも足りなければモデルを上げる**
   - 上げたモデルは、下で使った effort より低い所から始める【B】。
   - Opus を high より上げる前に、Fable を試す。Fable の high は、Opus の max と同じ程度の成績で、1 件の費用は約半分だった【B】。

## effort の目安
- Opus 5.5 は medium から始める【B】【O】。
  - medium は high より約 2.5 点低く、費用は約 70%。
  - low は約 8 点低く、費用は約 1/3。
  - xhigh は high より約 1.4 点高く、費用は 2.5 倍。
  - （SWE-bench Pro の値）【B】
- xhigh と max は、測って効果を確かめた作業だけに使う【O】。
- effort の名前は、モデルが違えば同じ量の考えにならない。あるモデルで合わせた強さを、別のモデルに引き継がずに比べ直す【F】【O】。
- Fable 5.2 の段の使い方【F】：
  - low：明確な作業、大量の作業（速くて賢いサブエージェント）
  - medium：対話しながらのコーディング、日常の作業
  - high：難しいコーディング・調べもの・長い無人の実行
  - 伸びの大部分は high で得られる。
- 考える量を減らしたいなら、指示で「考えずに答えて」と書くのでなく、effort を下げる。指示では思考は止まらない【F】【O】。
- effort は答えの長さにほとんど効かない。長さと調子は言葉で指定する【F】。
- low や medium で長い作業を任せるときは、下の「終わるまで止まらない」を必ず入れる。effort が低いほど、早く止まりやすい【F】。
- 機械的で、結果を自分で確かめられる作業は、1 段下げる（`effort: "lower"`）【運用】。

## 作業 → モデルの目安
| 作業 | モデルと effort | 注意 |
|---|---|---|
| ファイル探し・ログ読み・テストを回して結果を読む・要約 | Haiku か Sonnet（既定）【B】 | 間違いが見つけやすい作業に限る。判断とコードの編集はメインに残す。小さいモデルが読み違えると、メインが誤ったファイルを開いて、かえって高くつく【B】。読むだけなら「ファイルを変えない」と書き、道具を絞る【B】 |
| 分類・タグ付け・抽出の大量処理 | Haiku（medium）【B】 | 指示が 100K トークンを超えると単価が 5 倍になる。それでも Sonnet の 1/4。毎回長い指示が要るなら、1 件を仕上げる費用で Sonnet と比べる【B】 |
| 範囲の決まったコーディング（バグ直し・仕様どおりの機能） | Sonnet（medium → 難しければ high）【B】 | 移行や性能の最適化は、仕様がはっきりしていても難しいことがある → Opus、大きければ Fable【B】 |
| 繰り返しのエージェント作業（調べもの・レビュー・下書き） | Sonnet（medium）【B】 | |
| 日常の文書・スライド・表計算 | Sonnet（Claude Code では medium）【B】 | 込み入った財務の表や、大量の資料からの文書は Opus から【B】 |
| ふだんのコーディング・デバッグ・複数の PR にまたがる機能・迷ったとき | Opus（medium → high）【B】 | |
| 画像・スクリーンショット・コンピューター操作が中心の作業 | Opus（medium）【B】 | 最も低い effort でも、図の値の読み取りは前の世代の最高の effort を上回った【O】。細部の見落としが問題になる見直しは Haiku にしない【運用】 |
| 大きなリファクタ・移行・設計の計画・多くのサブエージェントの指揮・深い調べもの・長い無人の実行 | Fable（medium → high）【B】 | Opus の high でも足りないとき【B】。他のモデルの計画役・まとめ役として、試した人が良い結果を得た【F】 |
| 1 つの文脈を超える大きな分割作業（大量のソースの監査など） | Opus がまとめ、Sonnet の作業者を並列に【B】 | 例では、Opus 単独より約 1/3 安く、成績はほぼ同じ【B】。1 本につながった作業や、1 つの文脈に収まる作業には使わない【B】 |

- 文章を書く作業の指針は、出典にある。
  - 文書・下書きは Sonnet【B】。
  - 報告の書き方は、下の「報告は、文脈を知らない読み手に向けて書かせる」【F】。
  - 名前の案や、パネルの人物を演じる作業には、出典に指針がない。仕上がりを比べて選ぶ【運用】。
- 組み込みの Explore は、セッションのモデルで動く。安く回したいなら、`model: haiku` を指定した自分の定義を置くか、Agent ツールの `model` で Haiku を指定する【B】。
- 組み込みの Plan エージェントは、プランモードの中で計画の前に文脈を集める、読み取り専用の調べもの係。起動するときに CLAUDE.md を読まない。モデルはメインを引き継ぐ。リポジトリの決まりに沿った計画を立てさせたいときは、general-purpose のエージェントに `model` を指定して任せる。出典は Claude Code のドキュメント「Create custom subagents」：https://code.claude.com/docs/en/sub-agents
- `opusplan` は、計画を Opus、実行（コードの編集）を Sonnet にする。上の方針とは逆なので、既定にする前に測る【B】。

## モデルを替えるとき
- キャッシュは、書いたモデルのもの。新しいモデルの最初の回は、会話全体を書き直す分がかかる【B】。
- 区切りで替える。替える前に `/compact` するか、短い計画を書いて新しいセッションを始める【B】。
- 下のモデルへ替えると、上のモデルの考えの記録が読めず、前の推論を失う。Fable から他のモデルへ替えると、たいてい失う【B】。
- メインのモデルは、作業の途中では替えない【運用】。

## 任せる指示の書き方
- **終わるまで止まらない、と書く**【F】【O】
  - 頼んだ作業が残っている間は止まらない。
  - 途中の報告や質問はしてよい。ただし、答えに左右されない作業は止まらずに進める。
  - 方向を聞く・待つと申し出る代わりに、次の部分へ進む。
  - エラー・時間切れ・ロック・空の結果・失敗するツールは、まず原因を調べる。本当に止まるものでなければ、待つ・やり直す・直す・別の道具を使う、で越える。
  - 意図的に禁じられたもの（触るなと書いたファイル・与えていない権限・安全の仕組み）には手を付けない。見つけたことをはっきり書き、別の安全な方法を探す。
  - 止まってよいのは、人の入力なしには進めないときと、意図的に禁じられたものに当たったときだけ。
  - この一文で、取り消しにくい操作の確認は消えない。確認は別に残す。
  - 入れても、「残りの作業を並べてから止まる」終わり方は残る。出力は約 3 割増える【F】。
- **許可は中身で書く**
  - 「続けて」とだけ返さず、何を求めているかを書く。例：「はい、ステージングのデータベースでマイグレーションを実行してください」【F】。
  - 承認の決まりを書くなら、もう一度確かめてほしい操作を具体的に挙げる【F】。
  - 承認の要らない日常の手順は、並べて書く。「もっと自由に」だけでは曖昧【F】。
  - 承認の要るものに「外の人へのメッセージ」を入れると、日常の頼みごとの約半分を控えた【F】。止めたいのが「外への公開」なら、範囲を絞って書く。
  - してよいこと（コミット・push・PR・ラベル）と、してはいけないこと（main への push・実機・外への公開）を名指しする【運用】。
- **慎重さを積み重ねない**【F】
  - 古いメモや決まり（「決して再試行しない」など）は消す。
  - 「最初のエラーで止まってレビュー」のような止まる条件は、消すか範囲を絞る。
  - 「決して」は絶対に効く。「ファイルを決して消さない」でなく「ファイルを消す前に確かめる」と、範囲と理由を添えて書く。
  - 理由が当てはまらなくなった注意は消す。文の書き方の厳しい規則（「1 文 20 語以内」など）は、文がぎこちなくなるので外す。
- **持ち主かどうかを決めて書く**【F】
  - 重なったコードをまとめてほしいときだけ、「このコードの持ち主で、設計は任せる」と書く。
  - 入れると、重なりをまとめる率は 10% 未満から約 75% に上がる。一方で、出力が 7〜8 割増え、頼まないテストや文書が入り、既存の動きが変わることもあった。
  - 最後の要約では、小さな変更が省かれやすい。差分と要約の両方を見る。
  - 最小の変更でよいときは書かない。「ついでの直しはしない」は、この一文を打ち消さない。
- **報告は、文脈を知らない読み手に向けて書かせる**【F】
  - 読み手は、ツールの呼び出しもファイルも見ていない。報告だけで意味が通るように書く。
  - 要点を最初の数文に置く。後で説明する言葉を、先に使わない。
  - 作業中に作った用語や略語は使わない。
  - 短い文で、一文に一つの考え。能動態で、同じものには同じ語を使う。
  - 並ぶものだけ箇条書きにし、つながった考えは文で書く。
  - 何をした・何が分かった・何が要るかを書かせる【O】。
  - テストの失敗・飛ばした手順は、そのまま書かせる【運用】。
- **考えを答えに書き出させない**
  - 推論を答えの文に書き出させる指示は、拒否の元になる【F】【O】。
  - 短い説明や、何をしたかのまとめはよい【O】。
- **始めたものが動いている間は、終わったことにしない**【O】
  - 裏のコマンドやサブエージェントが動いている間は、その作業を終わったものとして扱わない。終わるのを待ち、出力を受け取ってから続ける。
  - 止まった作業を自動で続けさせるのは、同じ作業で 2〜3 回まで。そのあとは止める。
- **探してから動かす**【O】
  - 必要な情報が依頼文に書かれていない作業では、動く前に関係する場所を広く見るよう指示する。
  - 見つけた中身に従って動くので、信頼できない中身を読ませる場所に置かない。
- **時間を伝える**【O】
  - 見積もれるなら、時間の予算を伝える。予算があると、並列の作業がかなり早く終わった。
  - 予算は目安で、超えても止まらない。確実に止めるには、別に時間切れを置く。
- **委任の指示を見直す**【F】
  - サブエージェントを出しすぎるときは、スキルや指示ファイルの委任の行を見直す。
  - 委任の説明には、費用への影響・任せる価値がある場合とない場合・指示の渡し方を書く。

## 測る【B】
- 選びに迷う繰り返しの作業は、実際の作業を何件か選び、それぞれに合否の確かめ方を付ける。
  - 候補のモデルごとに、2〜3 の effort で、別々のセッションで回す。
  - 1 件を仕上げる費用と成績を並べて比べる。
  - いちばん難しい作業の費用も見る。20 問の例では、2 問が費用の 43% を占めた。
- 手軽には、同じ作業を `/model` で 2 つのモデルで回し、`/usage` を比べる。1 回の印象で決めない。
- 結果を自動で確かめられるなら、全部を low で回し、落ちたものだけ high でやり直す。例では、約 97% 通って 1 件約 $0.17 だった。全部を high にすると 95.3% で 1 件 $0.29 だった。
- 複数のモデルを組む形は、どの単一のモデルよりも良いときだけ残す。
