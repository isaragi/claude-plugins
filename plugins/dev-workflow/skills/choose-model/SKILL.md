# サブエージェントのモデルと指示を決める

出典：Anthropic のブログ「Which Claude model should you build with?」（2026-11-09）、ドキュメント「Prompting Claude Fable 5.2」「Prompting Claude Opus 5.5」。数字は出典が自社の計測として挙げたもの。作者やリポジトリの決まり（CLAUDE.md）と食い違ったら、そちらに従う。

## 決める順
1. **任せるかどうか**：1 つの文脈に収まる作業・手順が 1 本につながった作業は、任せない（分ける・まとめる手間が上回る）。任せるのは、互いに依存しない作業、メインの文脈を汚す大量の読み込み（ファイルの総ざらい・ログ・長い出力）、別の目で見てほしいもの。
2. **確かめる手段を先に用意する**：テスト・ビルド・スクリプト・はっきりした合否の基準。足りないと感じたら、モデルを上げる前にこれを足す。
3. **effort を 1 段上げる**（`lower`／`higher`）。effort で知識や技能は増えない。high を超える 1 段は、上のモデルに替えるのと同じくらいかかる。
4. **それでも足りなければモデルを上げる**。上げたモデルは、下で使った effort より低い所から始める。

## 作業 → モデルの目安
| 作業 | モデル | 理由・注意 |
|---|---|---|
| ファイル探し・grep・ログ読み・テストを回して結果を読む・要約 | Haiku（量が多い・形が決まっている）か Sonnet | 間違いが見つけやすい作業に限る。長いエージェントのループには向かない。読むだけなら「ファイルを変えない」と書き、道具を絞る |
| 分類・タグ付け・抽出の大量処理 | Haiku | 指示を 100K トークン以下に保つ（超えると単価が 5 倍） |
| 仕様がはっきりした定型の作業（決まった手順の撮影・UI テストの実行と読み取り・仕様どおりの直し・調べもの・レビュー・下書き） | Sonnet（effort は既定） | 移行や性能の最適化は、仕様がはっきりしていても難しいことがある → Opus |
| ふだんのコーディング・設計・判断・迷ったとき | Opus（既定 medium、足りなければ high） | メインの既定。コードを書くこと・判断はメインか Opus に残す |
| 画像・スクリーンショット・図の読み取りが中心の作業 | Opus | 視覚に強い。細部の見落としが問題になる見直しは、Haiku にしない。Haiku は「写っているか／ないか」のような答え合わせがやさしい確認だけ |
| いちばん難しい作業（大きなリファクタ・移行・設計の計画・多くのサブエージェントの指揮・深い調べもの・長い無人の実行） | Fable | Opus の high でも足りないとき。計画役・まとめ役としても強い |
| 大きな分割作業（大量のソースの監査など） | Opus がまとめ、Sonnet の作業者を並列に | 出典の例では、Opus 単独より約 1/3 安く同じ質。1 つの文脈に収まるなら使わない |

- 文章・名前の案・パネルの人物のような「書く」作業は、出典に専用の指針がない。仕上がりを比べて選ぶ（下の「測る」）。
- Claude Code の組み込みの Explore は、セッションのモデルで動く。安く回したいなら Haiku を指定する。
- モデルを切り替えると、キャッシュはモデルごとなので、最初の回は会話全体を書き直す分がかかる。メインのモデルは途中で替えない。

## 任せる指示の書き方
- **終わるまで止まらない、と書く**：頼んだ作業が残っている間は止まらない。エラー・時間切れ・ロック・空の結果は、まず原因を調べて越える。止まってよいのは、人の入力なしには進めないときと、意図的に禁じられたもの（触るなと書いたファイル・与えていない権限・安全の決まり）に当たったときだけ。取り消しにくい操作の確認は別に残す。
- **許可は中身で書く**：「続けて」ではなく、何をしてよいか（コミット・push・PR・ラベル）、何をしてはいけないか（main・実機・外への送信）を名指しする。承認の要らない日常の手順は並べて書く。
- **「決して」は絶対に効く**：範囲と理由を添える（「ファイルを消す前に確かめる」のように）。古いモデル向けの慎重な決まり（最初のエラーで止まる・再試行しない）が残っていたら外す。
- **持ち主かどうかを決めて書く**：重なったコードをまとめてほしいときだけ「このコードの持ち主として設計を任せる」と書く（出典では、まとめが増えるかわりに出力が 7〜8 割増え、頼まないテストや文書も増えた）。最小の変更でよいときは書かない。「ついでの直しはしない」は、この一文を打ち消さない。
- **報告は、文脈を知らない読み手に向けて書かせる**：何をした・何が分かった・何が残ったか、を短く。テストの失敗・飛ばした手順はそのまま。
- **長さと調子は言葉で指定する**：effort は答えの長さにほとんど効かない。
- **考えを答えに書き出させない**：推論の書き出しを求める指示は、拒否の元になりうる。
- **待つものがあれば待たせる**：裏のコマンドやサブエージェントが動いている間は、終わったことにしない。自動でやり直させるのは同じ作業で 2〜3 回まで。

## 測る
- 選びに迷う繰り返しの作業は、同じ実際の作業を 2 つのモデル（か 2 つの effort）で回し、仕上がりと使った量（`/usage`）で比べる。1 回の印象で決めない。
- 結果を自動で確かめられるなら、全部を低い effort で回し、落ちたものだけ高い effort でやり直す（出典では、全部を高くするより安く、成績も上だった）。
